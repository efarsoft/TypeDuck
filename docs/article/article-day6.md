# Day 6 竞品调研驱动的深度打磨——从能用到好用

> 「造个轮子！排版鸭 TypeDuck」系列教程 · 第 8 篇（收官篇）
> 前置阅读：Day 5《从写完到见面，只差一个按钮》（公众号历史消息可查）

Day 5 结束时，排版鸭的功能清单已经很完整了：编辑、AI、主题、热点、配图、草稿箱直发。从"功能有没有"的角度，该有的都有了。

但**「有」和「好用」之间，隔着一整个 Day 6**。

今天不讲新功能，讲三件事：怎么用调研找到差距、怎么用分析发现隐患、怎么用打磨补齐体验。最后收官。

---

## 一、竞品调研：不是抄，是定位

### 1.1 逐家调研了什么

我逐个调研了六个同类产品（品类泛称）在 2026 年 8 月的现状，维度包括收费模式、登录要求、AI 能力、数据路径、开源状态。全部来自官网、帮助文档和 GitHub 的交叉核实。

结论做成一张七列对比表，放在了首页。不点名具体产品，只用品类泛称。核心发现：

- **Markdown 排版工具**：基础免费但主题/导出常要会员，AI 云端按档收费
- **模板富文本编辑器**：模板生态最大，但 AI 写作和 AI 排版是两套独立会员
- **后台增强插件**：嵌公众号后台免跳转，但价格不透明且强依赖认证号
- **免费开源编辑器**：免登录、本地优先，但无 AI、功能面窄
- **AI 技能类**：全流程自动化 + BYOK，但排版只有几套主题

### 1.2 调研带来的三个决策

**决策一：做图片管线。** 所有竞品都有图床能力，而排版鸭的外链图片在公众号里不显示——这是最大的体验短板。

**决策二：不做 `:::` 模块的 UI 入口。** 调研发现 md2wechat 有 53 个模块，说明这个需求存在。但排版鸭的目标用户是非技术创作者，让他们学 `::: tip` 语法方向反了。模块引擎保留（AI 自动用），UI 不做。

**决策三：设置收敛。** 用 AI 深度分析发现设置入口有三套（各面板内嵌表单 + SettingsCenter），统一到 SettingsCenter 一处。

> 💡 **带走的知识点**：竞品调研不是"看别人做了什么我抄什么"，是**用别人的现状校准自己的定位**。找到"他们有我没有"的（是真需求还是伪需求？）、"我有他们没有"的（是差异化还是没人需要？），然后做减法比做加法更重要。

## 二、图片管线：Day 6 最重的功能

### 2.1 分层设计

图片在公众号创作流程中有两个不同的"时刻"：

- **写作时**：图片需要一个稳定 URL 供预览，且最好能跨平台复用（博客/掘金/知乎）
- **发布时**：微信只认自家素材库的 URL

分层方案：

```
写作层（可选）：
  配了图床 → S3 兼容直传（R2/OSS/COS）→ markdown 拿永久 URL → 多平台复用
  没配图床 → tdimg:// 本地暂存（IndexedDB）→ 预览时换 blob URL

发布层（自动）：
  扫描正文所有外链/本地图片 → 批量调微信 uploadimg → HTML 层回写微信 URL
  → 草稿里图片直接显示
```

关键设计：**markdown 源不被微信 URL 污染**。转传只发生在发布管线的 HTML 层，发完公众号后博客版照用不误。

### 2.2 S3 兼容：浏览器端 SigV4 签名

图床走 S3 兼容协议（一套通吃 R2/OSS/COS/minio），签名用 AWS Signature V4 在浏览器端完成——Web Crypto 的 `crypto.subtle` 实现 HMAC-SHA256 派生密钥链，**密钥不经过任何服务器**。

```typescript
// SigV4 核心四步
const kDate = await hmac(enc.encode(`AWS4${secretAccessKey}`), dateStamp)
const kRegion = await hmac(kDate, region)
const kService = await hmac(kRegion, 's3')
const kSigning = await hmac(kService, 'aws4_request')
// → 用 kSigning 签 canonicalRequest → 拼进 Authorization 头
```

这是纯前端工程里少见的"密码学实践"——不是加密，是签名。密钥留在用户浏览器里，上传直连云存储，排版鸭不碰数据。

### 2.3 踩的坑

**图片预览不显示**：`insertImage` 存完 IndexedDB 后忘了调 `rememberBlob`（创建 blob URL），Map 是空的 → 预览裂图。一行修复，但暴露了"插入 → 预览 → 刷新 → 切文档"四条路径都要测试。

**刷新后全部裂图**：启动时 `store.load()` 是 async 但没 await，图片恢复跑在数据加载前——竞态。同时切文档也不重新恢复。修复：`await store.load()` + `watch(activeDoc.id)` 重新 hydrate。

## 三、深度代码审查：AI 当安全顾问

### 3.1 发现了四个高危

用 AI 做了一次全项目的安全分析和代码审查，发现了四个实打实的问题：

| # | 问题 | 影响 |
|---|------|------|
| 🔴1 | `::: tip <img onerror=...>` 的标题直接拼 innerHTML | XSS 注入——导出的 HTML/PDF 无保护 |
| 🔴2 | 本地图片刷新后全部裂图 | hydrate 竞态 + 切文档不重新恢复 |
| 🔴3 | 图片存储永不回收 | 删文档不清 IndexedDB，blob URL 不 revoke |
| 🔴4 | 设置中心的三个开关保存后不生效 | "同步滚动"关了还在滚——欺骗用户 |

四个都修了。最有意思的是 #4——不是技术问题，是**产品信任问题**。一个"看起来能设置但实际不生效"的开关，比没有这个开关更伤信任。

### 3.2 顺手做的优化

- **复制检测本地图片**：含 `tdimg://` 的文章点复制会弹提示，引导用草稿箱发布——不再静默裂图
- **预览渲染防抖**：150ms 间隔，5000 字+文档按键不再卡
- **Electron 28 → 33**：Chromium 安全补丁追平
- **Ctrl+B/I/K 快捷键**：选中文字 Ctrl+B 加粗——肌肉记忆直接迁移
- **设置收敛**：配置统一到 SettingsCenter，各面板只显示"去设置"跳转

## 四、7 天收官总结

### 4.1 数据盘点

| 指标 | 数值 |
|------|------|
| 开发天数 | 7 天（日历 8 天） |
| 总提交数 | 30+ |
| 代码净增 | ~10,000 行 |
| 功能清单 | 编辑器 + 32 主题 + 10 项 AI + 热点选题 + 配图 + 草稿箱直发 + 官网 |
| 支持平台 | Web / Windows / macOS |
| 开源协议 | MIT |

### 4.2 架构一句话

**一个核心（core），两套外壳（web + desktop），所有能力 BYOK。**

```
core（零框架依赖）
  ├── markdown：渲染管线 + ::: 模块 + 主题注入
  ├── ai：OpenAI 兼容协议 + 流式 + 分层 Prompt
  ├── wechat：草稿箱直发 + 素材库转传
  ├── image：S3 兼容图床 + 免费图库搜索
  ├── hot：热榜聚合
  └── exporter：HTML / Word / PDF / Markdown
shared-ui（Vue 组件）
web（编辑器 SPA + 静态首页）
desktop（Electron 壳 + 主进程代理）
```

### 4.3 7 天里做对的三件事

1. **core 独立成包**——Day 2 桌面版只用 300 行新代码就搞定，因为 80% 逻辑在 core 里复用
2. **BYOK 而不是订阅制**——穷 + 隐私 + 自由，三个理由撑起一个产品价值观
3. **每天砍功能**——多轮对话、知识库、云同步、自动群发，都认真讨论后砍掉了；砍功能比加功能更能保证交付

### 4.4 公开 Roadmap

| 版本 | 内容 |
|------|------|
| v0.3 | 深色模式、移动端弹窗适配、阿里云 OSS 签名校准 |
| v0.4 | 自定义域名、编辑器搜索替换、`:::` 模块 UI（等真实需求长出来） |
| PRO | 独立产品，云同步/托管 AI/团队协作（开源版功能不会挪走） |
