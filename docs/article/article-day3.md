# 写不出、写不动、起不来标题？给排版鸭装上大脑

> 「造个轮子！排版鸭 TypeDuck」系列教程 · 第 5 篇
> 前置阅读：Day 2《桌面版 Electron 封装，复用 web 应用 80% 代码》（公众号历史消息可查）

先报战果。今天给排版鸭接上了 AI，从写标题到生成排版主题，一条龙：

- **编辑器工具栏多了四个绿按钮**：AI 润色 / AI 扩写 / AI 缩写 / AI 续写——选中文字就能用
- **标题栏旁边的 ✨**：一键生成 5 个候选标题，点击直接套用
- **AI 助手面板**：自定义指令（想怎么改就怎么说）、生成大纲、生成摘要
- **彩蛋：AI 生成排版主题**——「莫兰迪灰绿，安静的杂志感」，一句话，即刻拥有
- **BYOK 模式**：DeepSeek、豆包、通义千问、GLM、Kimi 五家预设 + 自定义端点，**用你自己的 API Key，内容不经过任何第三方服务器**

两次主提交约 2100 行新代码，核心链路从动手到能用不到一小时，剩下半天都在打磨细节和踩坑——坑也都记在下面了。

---

## 一、为什么是 AI？因为"排版"只解决了下游

Day 2 结束时，排版鸭已经能「写 → 排 → 复制到公众号」。但真用过才知道，一个公众号作者的完整链路是：

```
写什么 → 怎么写 → 写出来 → 排版 → 发布
```

排版工具只覆盖了最后两环。前面三环——选题、结构、文字——才是每天真正卡人的地方：标题想半小时，正文写三行，删了又改，改了又删。

所以 Day 3 的任务很明确：**把 AI 塞进写作流程里，让排版鸭从"排版器"变成"创作助手"**。不是加个聊天框那种塞法，是长在编辑器上：选中哪段就改哪段，光标在哪就从哪续写。

## 二、BYOK：为什么让用户自带 API Key

接入 AI 的第一个决策不是技术，是商业模式：**订阅制还是 BYOK？**

订阅制就是「用户付钱给我，我调接口赚差价」——主流做法，但对我这个独立开发者有三个死结：

- **穷**。作为个人开发者，我贴不起用户的 API 账单，定价低了亏死，高了没人用；
- **隐私**。订阅制意味着所有用户的文章内容都要经过我的服务器。一个标榜「本地优先」的工具，转头把正文往云上送，人设当场塌房；
- **自由**。今天 DeepSeek 便宜用 DeepSeek，明天想换 GLM 就换 GLM——订阅制把用户锁死在我选的模型上，BYOK 让用户自己说了算。

所以排版鸭选了 **BYOK（Bring Your Own Key）**：你在模型厂商那里注册、拿自己的 Key、用自己的额度，排版鸭只负责把 AI 的能力接进写作流程。Key 存在你电脑的浏览器本地存储里，**不经过任何服务器**——包括我的。

> 💡 **带走的知识点**：BYOK 不是省钱技巧，是责任边界的划分。用户的内容和账单都留在用户手里，工具只做管道。对独立开发者来说，它还顺手消灭了「跑路了用户的钱怎么办」这类问题——你没有收过钱。

## 三、一套 OpenAI 兼容协议，接所有厂商

Day 3 动手前的第一个问题：要对接 DeepSeek、豆包、通义千问、GLM、Kimi 五家，是不是得写五套接口？

答案是：**一套都不用多写。**

2026 年的现实是，国内主流大模型厂商全部提供 OpenAI 兼容端点。协议格式、鉴权方式（`Authorization: Bearer`）、流式响应（SSE），五家长得一模一样。所以排版鸭的整个 AI 客户端就一个函数：

```
POST {baseUrl}/chat/completions
```

每家厂商的差异，被压缩成了一条纯数据——一个预设对象：base URL、几个推荐模型 ID、Key 申请入口。**加一家新厂商 = 加一个对象，零行协议代码。**

这不是理论，是本项目当场验证过的：豆包预设是做完 DeepSeek/千问/GLM/Kimi 之后临时加的需求，最终改动是 9 行预设数据，1 行协议代码都没动。

当然，「兼容」不是完美的，踩到的差异都记在这：

- **智谱和 DeepSeek 的思考模式**会额外输出 `reasoning_content` 字段——解析时只认 `content`，忽略即可；
- **火山方舟**的 `model` 字段既能填模型名，也能填自部署接入点 `ep-xxx`，且模型名必须带日期后缀（`doubao-seed-2-1-turbo-260628`），短名直接 404；
- 各家 `/models` 接口的支持程度参差（见下一节）。

这些差异用一个宽容的解析器全能吸收，为它们分叉出五套代码不值得。

> 💡 **带走的知识点**：OpenAI 协议已经是 AI 时代的「事实标准」，就像当年的浏览器内核。选生态已经赢的协议，代码就只需要写一次——然后把省下的时间花在产品差异上。

## 四、模型列表不写死：/models 才是事实

第二个决策来得更狼狈一点。

给预设填「推荐模型 ID」的时候我做了一圈调研，结果被狠狠上了一课——**写死的模型列表，在 2026 年几乎必然是过期的**：

- DeepSeek 的 `deepseek-chat` / `deepseek-reasoner`，2026 年 7 月 24 日**已停用**（现在是 `deepseek-v4-flash` / `deepseek-v4-pro`）；
- Kimi 的 `kimi-k2` 全系，2026 年 5 月 25 日**已退役**（现在是 `kimi-k3`）；
- 豆包的模型名带日期后缀迭代，**厂商按月发新版**，任何快照都会过期。

如果一个排版工具把「模型选择」焊死在代码里，它半年后就会变成一个「只能用旧模型」的工具。模型的事实来源只有一个：**厂商自己的 `/models` 接口**（OpenAI 兼容格式，顺便这也是上一节协议红利的又一次兑现）。

所以排版鸭的最终方案分两层：

- **主来源：实时拉取。** 模型输入框旁有「获取模型列表」按钮，点一下 `GET /models`，成功后下拉更新为厂商当前的实时列表（顺带完成连通性验证）；
- **兜底：预置 ID。** 没拉取之前，下拉先显示预置的推荐模型——毕竟没填 Key 就调不了接口，总得让用户看得见候选；拉取失败也回退到这份兜底。

要不要自动拉？我们讨论后选择了手动触发：打开设置就悄悄发请求，对只是进来看一眼的用户不友好，也平添一次失败提示的尴尬。一个按钮，用户想刷新时自己点，意图明确。

顺手记两个实现细节：一是 `/models` 返回的不全是对话模型，embedding、语音、重排模型全混在里面（千问一次能拉回几百条），前端按命名模式过滤；二是拉取失败要把错误翻译成人话（401 是 Key 错、404 是地址或模型名错、`fetch` 直接抛是网络或跨域问题），别把原始 JSON 糊用户脸上。

> 💡 **带走的知识点**：配置数据分两类——**事实型**（会变，必须实时拉，如模型列表、价格）和**推荐型**（相对稳定，可以预置，如默认值）。分清这两类，就知道什么能写死、什么不能。

## 五、流式输出：「一个字一个字往外蹦」怎么实现

AI 功能的体验分水岭，就在「转圈等全部」还是「一个字一个字往外蹦」。后者的实现比想象中朴素，核心就三样：

**1. 请求时带 `stream: true`。** 服务端不再一次返回完整结果，而是把回答切成一小段一小段，用 SSE（Server-Sent Events）格式推送过来。

**2. 前端读流。** `fetch` 拿到的 `response.body` 是个可读流，一边收网络数据一边解析：

```typescript
const reader = response.body.getReader()
// 按行拆开，形如 "data: {...}" 的是增量，"data: [DONE]" 是结束
// 每段 JSON 里的 choices[0].delta.content 就是新蹦出来的几个字
```

每收到一段，就追加进任务状态里，界面靠响应式自动刷新——用户看到的就是文字往外冒，末尾还跟一个闪烁的绿色光标。

**3. 能停。** `AbortController` 传进 `fetch`，用户点「停止」就 `abort()`。有个细节要处理：中断时已经生成了一半的内容**按完成处理**，别把用户看了 20 秒的半成品直接扔了。

踩过的坑：智谱和 DeepSeek 的思考模式会在流里额外夹带 `reasoning_content` 字段（思考过程），解析时只认 `content` 就好；另外流是按「块」到达的，一行数据可能被劈成两半，得维护一个缓冲区拼完再按行解析——这个漏了的话，长回答会随机丢字。

## 六、AI 是怎么嵌进页面的：哑编辑器 + 一份任务状态

写了九个 AI 动作（润色/扩写/缩写/续写/标题/指令/大纲/摘要/主题），编辑器组件**一行 AI 代码都没有**。架构上就三条规矩：

**编辑器是"哑"的。** 它不知道 AI 存在，只做两件事：工具栏按钮被点了，往上抛一个事件；对外暴露三个方法——拿选区快照、替换指定范围、在光标处插入。AI 的所有逻辑都在外层，CodeMirror 的封装没被打破。

**任务状态只有一份。** 所有入口（工具栏、✨按钮、面板卡片）触发的任务都进同一个 `runAiTask()`，产出都汇进同一个任务对象（动作/状态/已生成文本/选区位置）。所以流式展示、停止、重试、错误提示天然全动作统一——加新动作从不用重写这些。

**结果不自动回写，用户确认才落盘。** AI 产出先进面板「候审」，点了「替换选区」「插入到光标」「应用标题」才写回编辑器。回写时还校验文档没被切换过——防止把 A 文章的润色结果插进 B 文章。

「AI 是助手，不是替代者」这句话，落进代码就是这么三行规矩。

## 七、彩蛋：AI 生成主题——「描述风格，即刻拥有」

Day 2 研究四个开源项目的主题体系时，md2wechat 给过一个启发：**它的"AI 型主题"本质是一份详细的 AI 设计提示词**——mood、色板、逐元素样式规范。当时我们就留了话头：主题既然能被"描述"出来，接上 AI 之后「描述风格 → 生成主题」完全可行。Day 3 兑现。

先解决一个直觉疑问：**网页和客户端都是打包好的文件，怎么"新增"主题？** 答案是 Day 2 埋的伏笔——`registerTheme()` 运行时注册接口。打包文件里装的是"引擎"，主题是**数据**不是代码：一个纯 JSON 结构，没有任何函数。AI 生成主题，就是往引擎的注册口里灌一份**经过消毒的数据**，引擎一行不动。

但"让 AI 直接写主题样式"是不敢的——JSON 里塞长 CSS 字符串是模型出错重灾区，而且等于把任意样式的注入口敞开了。最终方案是 Day 2 研究结论「**布局 DNA × 色彩皮肤**」的落地：

- **AI 只产出 13 个受控设计令牌**：主强调色、标题色、正文色、页面底色倾向、标题字体、标题形态、引用样式、链接样式、代码风格、圆角档位、疏密……全是枚举值和色值，白名单校验 + 正则检查 + 缺省补默认，**一个 CSS 字符都碰不到**；
- **本地三套布局模板**（简洁 / 卡片强调 / 文艺留白）把令牌编译成完整主题——模板是照着成熟主题的骨架写的，模型再怎么抽风，产出的排版结构也是合法的。

生成后先出预览卡（主题名 + 色板色块），点「保存并应用」才注册 + 写入本地存储（上限 20 套防膨胀）。主题面板多出一个「🤖 AI 生成」分组，可以删除；下次启动自动恢复。深色底色的令牌会自动反转正文色保可读。

一句话总结这个彩蛋：**AI 出皮肤，模板出骨架，引擎不动、数据常新。**

## 八、翻车与打磨实录

诚实清单，今天踩的坑按时间排：

- **一个消失的闭合括号**。给流式函数加新动作时，编辑操作不小心吃掉了 `switch` 的右括号，esbuild 报了个不知所云的 `Unexpected "export"`。排查五分钟，教训是：大段重构后先跑一遍构建再继续。
- **datalist 的浏览器顽疾**。模型下拉最早用的原生 `datalist`，结果模型列表点按钮拉取成功了、下拉里纹丝不动——浏览器对「JS 动态更新 datalist 选项」的支持一塌糊涂，且各家行为不一致。换成自绘下拉（输入框可手填 + 箭头弹列表），数据一更新立刻可见。
- **设置弹窗的误伤**。最初点弹窗外的空白处会关闭弹窗，填 Key 填一半被误触关掉，火气很大。改成只有 ✕ 和「完成」能关。
- **一堆小打磨**：AI 按钮统一加「AI」前缀和普通格式按钮区分；✨ 生成标题挪到标题输入框旁边（视觉上成为标题的一部分）；右侧三个面板按钮支持再次点击收起；AI 按钮组在工具栏强制换行，不和格式按钮挤一行。

每个都不大，但加起来就是「能用」和「顺手」的差距。

## 九、今天没做什么（同样重要）

- **多轮对话/聊天面板**：不做。排版鸭是写作工具，不是 ChatGPT 套壳，定位漂移比功能缺失可怕；
- **AI 配图**：不做。多模态生成的 BYOK 复杂度陡增，且公众号作者大多用外部工具出图（Day 4 会有更实用的配图方案）；
- **选题/热点引擎**：Day 4 的正菜，今天不抢戏；
- **知识库 RAG**：超范围，砍。

## 今日总结

| 决策 | 理由 |
|------|------|
| BYOK 而非订阅制 | 独立开发者贴不起账单；本地优先的人设不容内容出域；用户换模型自由 |
| 一套 OpenAI 兼容协议 | 五家厂商协议趋同，差异压缩成纯数据预设；加厂商 = 加对象 |
| 模型列表实时拉取 | 写死必然过期（deepseek-chat 停用、kimi-k2 退役都是现成证据）|
| AI 只出设计令牌 | CSS 字符串是模型出错重灾区；白名单 + 模板编译保质量下限 |
| 结果候审再回写 | AI 是助手不是替代者；文档切换校验防串稿 |
