## 素材一：一个 `!important` 的悬案

（本节内容来自 Day 2 主题系统开发时的真实踩坑，Day 3 成文时并入正文）

### 事情的起因

为了对抗微信公众号编辑器清洗样式，我们给渲染管线的**每一条内联声明都加上了 `!important`**——这是从 WeChat-Markdown（30 套主题的成熟项目）那里抄来的实战经验。

抄的时候我们问了自己一个问题：**这真的有必要吗？**

### 反方：CSS 级联告诉你这是画蛇添足

浏览器级联规则里，内联样式的优先级**天然高于所有选择器**——class、id、标签选择器统统压不过它。所以「防止公众号前台的普通 CSS 覆盖」这个理由不成立：不加 `!important`，内联样式照样赢。

如果微信只是用普通样式表渲染文章，那这层加固纯属多余，还带来三个代价：

- HTML 体积膨胀（每个声明多 11 个字符，长文可观）
- 用户手工改 HTML 时的心智负担
- **对 Word 导出是毁灭性的**（见下）

### 正方：两个真实场景

**场景一：微信暗色模式的强制反色。** 微信客户端在暗色模式下会用自己的 `!important` 声明强制改文字颜色（保护夜间可读性）。而级联规则的完整优先级是：

```
内联 !important > 样式表 !important > 普通内联 > 普通样式表
```

也就是说，**只有「内联 + !important」双重加持才能顶住微信的暗色反转**，保住主题的品牌色——否则「咖啡屋」的暖棕在读者手机的夜间模式里可能被微信染成灰白。

**场景二：编辑器粘贴规整。** 公众号编辑器粘贴富文本时会解析、规整、重写一部分样式。经验上带 `!important` 的声明更不容易被「顺手」改值——注意，这是经验性结论，不是规范保证。

### 代价是真实的：Word 导出阵亡

我们实际踩到的坑：**Word 的 HTML 导入器不识别 `!important` 语法**，遇到就解析异常，导出的 docx 排版全部错乱——标题字号丢失、表格线消失、颜色复位。

解法是**双轨渲染**：

```typescript
// 渲染管线支持两种产物
render(markdown, theme, { important: true })   // → 复制到公众号 / 预览 / 导出 HTML
render(markdown, theme, { important: false })  // → 导出 Word（干净版）
```

同一次渲染请求，按出口选择样式强度。这也是一个架构教训：**「兼容性补丁」不要焊死在渲染内核里，要做成可配置的出口策略**——否则每个新出口（docx、PDF、小红书图片……）都要跟全量的历史补丁打架。

### 悬案的部分：留给读者一个实验

「场景一」（暗色反色）目前是**理论 + 同行的经验**，我们还没有亲手验证过。这里有一个任何人都能做的实验：

1. 同一篇文章，用排版鸭导出两份 HTML：带 `!important` 版和干净版（改一下源码或用「导出 HTML」对比「复制到公众号」）
2. 两份分别粘贴到公众号后台，群发或预览到手机
3. 手机切换暗色模式，对比文字颜色是否被反转

如果干净版的颜色被反转而加强版安然无恙，`!important` 的存在就是被证实的必要；如果两者没区别——那我们就该把它删掉，白赚更干净的 HTML。

**结论当前状态：存疑但保留，代价已被双轨方案归零。** 工程上很多兼容性决策都是这样：无法立刻证伪、删除成本大于保留成本时，隔离它、标注它、留一个能证伪的实验给未来。

### AI 生成自定义主题（研究沉淀的落地）

- 每主题独立文件夹（`themes/<id>/index.ts`），结构自包含
